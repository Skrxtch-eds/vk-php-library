# Адверсариальное ревью

Это отчёт первого раунда до исправлений. После повторного запроса пользователя три находки исправлены; независимая перепроверка описана в [FIX_VERIFICATION.md](FIX_VERIFICATION.md). Исторические результаты ниже относятся к исходной версии. Скрипт `poc.php` теперь показывает поведение текущего кода; потеря ответа в модели ограничена первой попыткой.

Проверено 22 октября 2026 года. Исходники, штатные тесты, README и конфигурация после ревью не исправлялись. Добавлены только этот отчёт и `review/poc.php`.

PoC проверены на PHP 8.1.34 и 8.4.27. HTTP заменён локальными заглушками, все токены вымышлены. Запросов к VK и реальных отправок не было. Поэтому ниже доказано поведение библиотеки при указанных входах; работа устаревшего метода на сервере VK не проверялась.

## Запуск

Из корня проекта после `composer install`:

```bash
php review/poc.php
php review/poc.php trace
php review/poc.php trace-no-args
php review/poc.php rotation
php review/poc.php legacy
```

Скрипт не входит в PHPUnit suite. В использованном рабочем окружении запускался так:

```powershell
& '..\.runtime\vk-php81\php.exe' review\poc.php
& '..\.runtime\vk-php\php.exe' review\poc.php
```

## 1. P2 — токен сохраняется в аргументах трассировки исключения

**Место:** `src/Internal/ApiTransport.php:37` (изменение аргумента `$parameters`), исключение доступа создаётся на строках 87–88.

**Триггер:** `zend.exception_ignore_args=0`, затем обычный ответ VK с ошибкой доступа 15. При обработке исключения приложение выгружает `getTrace()` или делает `var_dump($error)`.

**Фактический результат:** `getMessage()` безопасен, но в кадре `ApiTransport::request` остаётся массив с полным `access_token`. `var_dump()` исключения тоже содержит токен. Ответ заглушки содержит только код ошибки; секрет приходит из самой библиотеки, а не из отражённого текста сервера. Защита `AccessToken::__debugInfo()` здесь не участвует: трассировка хранит уже строку.

**Ожидаемый результат:** исключения безопасно передавать в диагностический сборщик без сырого токена в аргументах внутреннего вызова.

**PoC:** `php review/poc.php trace` на обеих версиях:

```text
exception=VkLibrary\Exception\AccessDeniedException
message_contains_token=no
trace_contains_raw_access_token=yes
var_dump_exception_contains_token=yes
```

**Условия риска:** включённое сохранение аргументов и выгрузка структурированного исключения в журнал/отладочную страницу. Сам вызов API не отправляет токен постороннему серверу. Контрольный запуск `trace-no-args` с `zend.exception_ignore_args=1` выводит `trace_contains_raw_access_token=no` и `var_dump_exception_contains_token=no`. Явный `var_export(AccessToken)` и дампы памяти не использованы как доказательство. [PHP: настройка сохранения аргументов исключений](https://www.php.net/manual/en/ini.core.php#ini.zend.exception-ignore-args).

## 2. P2 — повтор может отправить одно сообщение от другого владельца токена

**Место:** `src/Internal/ApiTransport.php:35–37`: источник токена читается заново внутри цикла попыток.

**Триггер:** VK принял сообщение от A, но HTTP-ответ потерялся. До следующей попытки источник токена начинает возвращать токен другого отправителя B. Это возможно у внедрённого динамического `TokenProvider`; PoC использует штатный `EnvironmentTokenProvider` и смену переменной из внедрённого `Sleeper`.

**Фактический результат:** следующая попытка сохраняет `random_id`, но меняет `access_token`. Локальная модель дедупликации по отправителю и `random_id` принимает две доставки. Вызов возвращает ID второй и сообщает об успехе:

```text
returned_message_id=2
delivered=[{"sender":"FAKE_SENDER_A","peer_id":123,"random_id":456},{"sender":"FAKE_SENDER_B","peer_id":123,"random_id":456}]
```

**Ожидаемый результат:** одна логическая операция сохраняет исходного отправителя во всех попытках либо завершается явно при смене личности. Обновление источника для последующего публичного вызова не должно менять отправителя уже выполняемой операции.

**PoC:** `php review/poc.php rotation`; одинаковый результат на PHP 8.1 и 8.4. Это локальная модель известной области действия `random_id`, а не наблюдение двух доставок на рабочем VK. [Официальное описание параметра VK](https://dev.vk.com/ru/method/messages.send).

**Условия риска:** токены должны принадлежать разным отправителям. Простое обновление токена того же владельца этот сценарий не доказывает. Стандартный `AccessToken` неизменяем; при его использовании воспроизведения нет. У штатного `NativeSleeper` нет смены переменной окружения: PoC воспроизводит разрешённую DI-конфигурацию с динамическим источником.

## 3. P2 — исходящее legacy-сообщение приписывается получателю

**Место:** `src/Internal/ResponseMapper.php:72`: `from_id` безусловно заменяется на `user_id`, поле `out` не учитывается.

**Триггер:** старый формат личного диалога: `user_id=123`, `out=1`, `from_id` отсутствует; авторизованный пользователь имеет ID 999. В таком формате `user_id` обозначает собеседника, а `out=1` — исходящее сообщение.

**Фактический результат:** библиотека возвращает `Dialog(peerId=123)` с `lastMessage->fromId=123`. Получатель записан как автор собственного исходящего сообщения.

**Ожидаемый результат:** отправитель 999 либо явное отсутствие сведений об отправителе. Возвращать получателя как подтверждённого автора неверно.

**PoC:** `php review/poc.php legacy` на обеих версиях:

```text
peer_id=123
actual_sender=123
expected_sender=999 (or unknown; recipient 123 is not the sender)
```

**Условия риска и граница доказательства:** ошибка относится к поддерживаемому в коде старому формату с `user_id`/`body`, включая явно выбранную старую `apiVersion`. Она воспроизведена на локальном ответе этого формата. Это не доказательство того, что сервер сейчас выполняет `messages.getDialogs` версии 5.80. Уже описанное в README прекращение поддержки старого метода не считается отдельной находкой. В режиме `Conversations`, где присутствует `from_id`, этот PoC не применяется. [Описание полей старого формата в документации автора клиента rvkstat](https://www.rdocumentation.org/packages/rvkstat/versions/2.6.3/topics/vkGetUserDialogs).

## Что не объявлено найденными уязвимостями

Фиксированный HTTPS-хост, проверка TLS и запрет редиректов в cURL по чтению кода не обходятся пользовательскими опциями. Попытки подменить `access_token`, `peer_id` и `v` через `sendMessage()` отвергаются. При неизменном токене внутренние повторы сохраняют `random_id`. Утечка из одного только `getMessage()` не обнаружена. Эти выводы не заменяют сетевого теста cURL с сервером VK.

Критических проблем P1 в проверенных сценариях не доказано. Найденные проблемы оставлены без исправлений по условию задания.
