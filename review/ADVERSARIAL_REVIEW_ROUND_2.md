Статус после следующего запроса пользователя: описанная ниже P3 исправлена. `chat_id` проверяется до сложения; текущий `poc_round2.php` возвращает `InvalidResponseException`. Результаты исправления находятся в [FIX_VERIFICATION.md](FIX_VERIFICATION.md). Сам отчёт ниже сохранён как история второго раунда.

Дата: 22 октября 2026 года. Проверена окончательная версия с обработкой исключений в трёх публичных методах `VkClient` и фабрикой `Internal/SafeException`.

**Вердикт:** три исходные ошибки устранены в проверенных сценариях. Новых подтверждённых проблем P1/P2 в окончательной версии не обнаружено. Осталась одна небольшая ошибка классификации некорректного ответа, P3, описанная ниже. Это ограниченная локальная проверка, а не доказательство отсутствия любых дефектов.

Исходники, штатные тесты, README и конфигурация этим ревью не изменялись. Добавлены только этот отчёт и `review/poc_round2.php`. Использованы вымышленные значения, локальные HTTP-заглушки и заменённое ожидание. Сеть и реальные отправки не использовались.

## Вердикт по трём исправлениям

1. **Токен в исключении: исправлено для публичного API.** Новое исключение создаётся после HTTP и разбора DTO. `SafeException::create()` принимает только имя класса и числовой код; исходное исключение и `previous` не переносятся. Обычная ошибка доступа, сбои зависимостей, неверный envelope и некорректный успешный `response` проверены тестами. `review/poc.php` на обеих версиях показывает `message_contains_token=no`, `trace_contains_raw_access_token=no`, `var_dump_exception_contains_token=no`. Найденный при промежуточном чтении обход через `ResponseMapper` в окончательной версии закрыт; новой открытой находкой он не считается.

2. **Смена отправителя при retry: исправлено.** `ApiTransport` получает токен один раз до цикла. PoC с изменяемым окружением возвращает ID 1 и одну доставку от `FAKE_SENDER_A`. Штатный регрессионный тест дополнительно подтверждает последовательность A/A при повторе, затем B в следующем публичном вызове, с одним чтением провайдера на операцию. Это локальная модель, не проверка дедупликации на сервере VK.

3. **Получатель вместо автора legacy-сообщения: исправлено.** Для `out=1` без `from_id` PoC возвращает `fromId=null`. Тесты подтверждают приоритет явного `from_id`, fallback `user_id` только при `out=0`, неизвестное направление как `null`, отклонение неверного `out` и варианты беседы.

## P3 — переполнение legacy chat_id теряет классификацию ошибки ответа

**Место:** `src/Internal/ResponseMapper.php:57`, сложение `2000000000 + chat_id`; наружная классификация в `src/VkClient.php:110`.

**Условия:** локальный HTTP-ответ имеет корректный JSON-envelope `response`, страницу с одной записью legacy и целочисленный `message.chat_id=PHP_INT_MAX`. Остальные необходимые поля сообщения корректны. Такое значение не является допустимым ID реальной беседы; проверяется устойчивость к некорректным данным.

**Ожидается:** `InvalidResponseException`, как для других неверных полей ответа и согласно таблице ошибок README.

**Наблюдается:** проверка минимального значения пропускает число, сложение переполняет PHP int и даёт float. При построении `Dialog` возникает внутренний `TypeError`; публичная граница безопасно заменяет его на общий `VkException('VK request failed.')`, код 0. Обработчик, который различает неверный ответ через `catch (InvalidResponseException)`, эту ветку не получит.

**Локальное воспроизведение:** из корня проекта `php review/poc_round2.php`. Если нужен autoload ASCII-копии, его абсолютный путь можно передать первым аргументом. На PHP 8.1.34 и 8.4.27 результат одинаков:

```text
observed_exception=VkLibrary\Exception\VkException
expected_invalid_response=no
message=VK request failed.
```

**Оценка и граница доказательства:** P3, небольшая ошибка корректности на некорректном ответе. Защитная граница продолжает работать: наружу не выходит исходный `TypeError` или его аргументы. Утечка секрета, неверная доставка или возможность сформировать такой ответ через обычное сообщение VK не доказаны. В режиме Conversations сложение legacy `chat_id` не выполняется.

## Ограничения

Доступность `messages.getDialogs` на сервере VK не проверялась и не объявляется новой проблемой: выбор legacy по умолчанию и его неопределённая доступность уже явно описаны в README. Чтение cURL-кода не заменяет проверку TLS и сетевого обмена; в этом ревью сеть намеренно не использовалась. Собственные журналы внедрённых зависимостей и переменные вызывающего приложения не покрываются защитой наружных исключений.
