# Проверка и исправление всех найденных ошибок

22 октября 2026 года основной агент самостоятельно запустил исходные PoC на PHP 8.1.34 и 8.4.27. Все три сценария подтвердились. Сеть не использовалась.

| Сценарий | До исправления | После исправления |
| --- | --- | --- |
| Ошибка доступа при `zend.exception_ignore_args=0` | Токен в `getTrace()` и `var_dump($error)` | Токена в этих представлениях нет |
| Потерян первый ответ, источник токена сменился с A на B | Две доставки в локальной модели, результат 2 | Одна доставка от A, результат 1 |
| Исходящее legacy-сообщение без `from_id` | `fromId=123`, где 123 — получатель | `fromId=null` |
| Переполнение `chat_id=PHP_INT_MAX` | Общий `VkException` вместо ошибки ответа | `InvalidResponseException` до сложения |

`ApiTransport` создаёт отдельный массив авторизованных параметров и читает токен до цикла повторов. На границе каждого публичного метода `VkClient` создаётся наружное исключение с безопасным текстом и новой трассировкой, сохраняя класс и код штатной ошибки. Старая цепочка `previous` не переносится. Неожиданные ошибки внедрённых зависимостей переводятся в `VkException` с фиксированным сообщением. Настройки PHP библиотека не меняет.

В промежуточной версии защита стояла только в транспорте. При повторном ревью обнаружилось, что некорректный успешный `response` может оставить секрет в аргументах `ResponseMapper`. Поэтому окончательная граница перенесена в `VkClient` и включает разбор DTO. Добавлены три регрессионных сценария для некорректных результатов `getUser`, `getDialogs` и `sendMessage`.

`Message::fromId` теперь имеет тип `?int`. В legacy-формате явный `from_id` сохраняется. Если его нет, `user_id` используется только при `out=0`; при `out=1` или неизвестном направлении возвращается `null`. Неверное значение `out` отклоняется.

Регрессионные тесты находятся в `tests/SecurityRegressionTest.php`. Они также проверяют, что новый публичный вызов читает обновлённый токен, входящие сообщения сохраняют автора, а сбои HTTP-клиента и некорректные ответы не раскрывают токен через исключения транспорта.

Повторить ручную проверку:

```bash
php review/poc.php
composer test -- --filter SecurityRegressionTest
```

В локальной модели потеря ответа происходит только на первой попытке. Двойная доставка на сервере VK не проверялась: доказаны смена токена в исходном коде и её устранение в исправленном.

Повторное независимое ревью подтвердило устранение трёх исходных ошибок. Отчёт находится в [ADVERSARIAL_REVIEW_ROUND_2.md](ADVERSARIAL_REVIEW_ROUND_2.md). Найденная в нём P3 исправлена по следующему запросу пользователя: перед преобразованием `chat_id` в `peer_id` проверяется, что сложение не переполнит PHP int. Некорректное значение вызывает `InvalidResponseException`.

Для P3 добавлены проверки `PHP_INT_MAX`, первого переполняющего значения, нуля, отрицательного числа, строки и float. Отдельный тест проверяет границу представимости int. До исправления два теста воспроизводили неверный класс исключения; после исправления проходят все. Подобных преобразований со сложением в других местах библиотеки не обнаружено.

```bash
php review/poc_round2.php
```

Ожидаемый результат: `observed_exception=VkLibrary\Exception\InvalidResponseException`, `expected_invalid_response=yes`, код завершения 0. Открытых ошибок из обоих раундов ревью не осталось.

Ограничения: защита исключений не скрывает токен в собственных журналах HTTP-клиента, переменных вызывающего приложения или дампе памяти.
